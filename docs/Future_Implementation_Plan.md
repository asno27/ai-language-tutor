## ✅ Phase 1.9: 백엔드 기능별 분리 — PC 의존성 제거 (2026-09-27 완료)

### 문제
- 현재 모든 AI 기능(오늘의 영어 추천, 번역, 영작 교정, 사전, 발음 평가, 뉘앙스 챗봇)이 **PC + ngrok**을 거칩니다. PC가 꺼져 있으면 전부 `Failed to fetch` 오류가 납니다.
- 원인: `js/api.js`가 PC 서버(`/api/llm`) 연결에 실패하면 Gemini를 브라우저에서 직접 부르는 예비 경로가 있습니다. 그런데 ① API 키가 `'dummy'`이고 ② Google이 허용하지 않는 `ngrok-skip-browser-warning` 헤더를 붙여 보내기 때문에 브라우저가 요청을 차단합니다(CORS). 즉 **예비 경로가 실제로는 한 번도 동작할 수 없는 구조**입니다.
- 그런데 PC(가정용 IP)가 꼭 필요한 기능은 유튜브 봇 차단을 우회하는 `/api/youtube`뿐입니다. 일반 AI 기능은 PC를 거칠 이유가 없습니다.

### 목표 구조

| 경로 | 담당 기능 | 호스팅 | PC 꺼져 있을 때 |
|---|---|---|---|
| `/api/llm` | 번역·교정·사전·오늘의 문장·발음 평가·뉘앙스 등 모든 AI 텍스트 기능 | **Cloudflare Workers** (무료, 서버리스) | ✅ 정상 작동 (24시간) |
| `/api/youtube` | 유튜브 자막·오디오 추출 (가정용 IP 필요) | 기존 그대로 PC + ngrok | ❌ "PC 서버를 켜 주세요" 안내 |

- **Cloudflare Workers를 고른 이유**: 무료 요금제로 하루 10만 요청까지 가능하고, Render 무료 서버처럼 잠들었다 깨느라 첫 요청이 30초 넘게 걸리는 문제가 없습니다. 대시보드에 코드를 붙여넣는 것만으로 배포되므로 Git이나 Node.js 설치가 필요 없습니다.
- API 키(Gemini, Groq)는 코드에 쓰지 않고 Cloudflare의 **암호화된 환경변수(Secret)**에 저장합니다.

### 구현 내용
1. **`worker/llm-worker.js` (신규)**: `server/main.py`의 `/api/llm` 로직을 그대로 옮긴 서버리스 함수.
   - 요청/응답 형식은 기존과 100% 동일 (`{ systemPrompt, userMessage }` → `{ success, data, source }`). 프론트엔드 프롬프트 코드는 수정할 필요 없음.
   - Gemini 1순위 → 실패(429·오류·파싱 실패) 시 Groq 2순위. JSON 정규식 추출(`\{.*\}`)도 동일하게 유지.
   - 모델 이름도 환경변수(`GEMINI_MODEL`, `GROQ_MODEL`)로 뺌. 모델이 단종돼도 코드 수정 없이 대시보드에서 바꿀 수 있음.
     ⚠️ 현재 `server/main.py`의 Groq 모델 `llama-3.1-70b-versatile`은 Groq에서 이미 서비스 종료된 모델로 알려져 있어, **지금은 Groq 예비 경로도 사실상 작동하지 않을 가능성이 높음.** Worker 기본값은 `llama-3.3-70b-versatile`로 두고, Groq 콘솔에서 현재 제공 모델을 확인해 환경변수로 지정.
   - 허용 출처(CORS): `https://asno27.github.io`와 로컬 개발 주소만 허용.
   - 입력 길이 제한(요청당 약 2만 자): 누군가 주소를 알아내 대량 요청을 보내 API 한도를 소진하는 것을 줄이기 위함.
2. **`js/api.js` 수정**:
   - AI 요청 순서: **① Cloudflare Worker → ② PC 서버(켜져 있으면 예비로 사용) → ③ 한국어 오류 안내.**
   - 동작하지 않는 브라우저 직접 호출 경로(`'dummy'` 키) 삭제.
   - 유튜브 요청 실패 시 `Failed to fetch` 대신 "유튜브 기능은 PC 서버가 켜져 있어야 합니다" 안내.
   - Worker 주소(`LLM_WORKER_URL`)가 비어 있거나 Worker가 실패하면 PC 서버로 넘어감 → Worker에 키가 등록되기 전에도 기존 동작이 깨지지 않음.
3. **`server/main.py`는 수정하지 않음**: PC 서버의 `/api/llm`은 예비 경로로 계속 남겨 둠.

### 배포 방식 (2026-09-27 확정)
- Cloudflare Worker `ai-language-tutor`가 GitHub 저장소 `asno27/ai-language-tutor`(main 브랜치)에 연결되어 있음. **저장소에 push하면 Cloudflare가 자동으로 `npx wrangler deploy` 실행.**
- 저장소 루트의 `wrangler.jsonc`가 배포 설정: 정적 파일(index.html, css, js, data)은 사이트로 제공하고, 정적 파일에 없는 요청(`/api/llm`)은 `worker/llm-worker.js`가 처리.
- `.assetsignore`로 `docs/`, `worker/`, `server/`, `*.py` 등은 사이트 파일에서 제외.
- 주소: `https://ai-language-tutor.kaipromp.workers.dev` (사이트) / `.../api/llm` (AI 서버). `js/api.js`의 `LLM_WORKER_URL`에 설정됨.

### 사용자가 직접 해야 하는 작업 (계정·키 관련이라 AI가 대신할 수 없음)
1. `wrangler.jsonc`가 포함된 커밋이 배포된 뒤, Cloudflare 대시보드 → **Workers 및 Pages → ai-language-tutor → 설정 → 변수 및 비밀**에서 추가:
   - `GEMINI_API_KEY` (유형: **비밀/Secret**)
   - `GROQ_API_KEY` (유형: **비밀/Secret**)
   - (선택) `GEMINI_MODEL`, `GROQ_MODEL` (유형: 텍스트)
   - ※ 빌드 설정의 "변수 및 암호"가 아니라 **런타임 "변수 및 비밀"**에 넣어야 함.
2. 등록 후 AI에게 "테스트해줘"라고 요청 → `/api/llm`에 실제 요청을 보내 확인.

### 완료 확인 기준
- PC 서버를 끈 상태에서 GitHub Pages 사이트의 '오늘의 영어 추천', 번역, 사전이 정상 작동.
- PC 서버를 끈 상태에서 유튜브 탭은 "PC 서버를 켜 주세요" 안내가 뜸.

## 🎯 Phase 2: 대화형/참여형 영어 학습 기능 구현

Phase 2에서는 단순히 입력한 텍스트나 영상을 번역하는 것을 넘어, 사용자가 직접 참여하고 말하며 피드백을 받는 능동적 인터랙션 기능들을 개발합니다. 모든 AI 로직은 이미 완벽하게 구축된 `server/main.py`의 듀얼 코어(Gemini/Groq) 시스템을 활용합니다.

### 2.1. 빈칸 채우기 퀴즈 및 역할극 (Interactive Role-play) — ✅ 역할극 완료 (2026-09-27)
> 구현 결과: '🎭 역할극' 탭. 상황 7개 + 직접 입력, 난이도 3단계, 매 대답마다 교정·점수·설명, 다음 대답 예시 칩, 🎤 말로 대답하기, AI 대사 자동 읽기. 한국어로 쓰면 영어 표현을 알려줌. 대화 기록은 저장하지 않음(새로고침 시 사라짐). 빈칸 채우기 방식은 "대답 예시 칩"으로 대체했으며, 별도 빈칸 퀴즈는 미구현.

- **기능 개요**: 사용자의 현재 영어 수준에 맞춰 상황(예: 공항 입국심사, 식당 주문, 스타벅스)이 주어지고, AI와 핑퐁식으로 대화하는 기능.
- **동작 방식 (기획 상세)**:
  1. **상황극 UI 추가**: `index.html`에 'Role-play' 탭을 신설하여 채팅(Chat) 형태의 인터페이스 구축.
  2. **프롬프트 템플릿 (`prompts.js`)**: `mode: 'roleplay'`를 추가하여, 백엔드 AI에게 특정 페르소나(예: "You are a friendly Starbucks barista")와 난이도 제약을 부여.
  3. **사용자 입력**: 사용자가 대답을 텍스트로 치거나 빈칸을 채워 넣음.
  4. **백엔드 연동**: 프론트엔드가 `/api/llm`으로 사용자의 응답을 전송하여, 문법 교정 점수와 상대방(AI)의 다음 대답을 JSON 형태로 받아 화면에 말풍선으로 렌더링.

### 2.2. PDF 인터랙티브 워크시트 (Interactive PDF Worksheet) — ✅ 완료 (2026-09-27)
> 구현 결과: 학습지 탭 상단 "📄 내 PDF로 학습지 만들기". pdf.js 6.3.289(cdnjs)로 브라우저에서 텍스트 추출 → 약 1,500자 구간(최대 10개)별 AI 분석(요약·핵심 단어 강조·빈칸 3개·쉐도잉) → 파일 해시 기준 캐시, 최근 PDF 8개 목록, 실패 구간은 다시 열 때 재시도. 스캔(이미지) PDF는 미지원.

- **기능 개요**: 1~10주 차의 워크시트 내용이나 토익/토플 지문이 담긴 PDF 파일을 업로드하면, AI가 지문을 분석하여 자동으로 빈칸 채우기, 섀도잉 평가, 단어장을 동적 생성하는 기능.
- **동작 방식 (기획 상세)**:
  1. **PDF 파싱**: 프론트엔드에서 `pdf.js` 모듈을 사용하여 업로드된 PDF의 텍스트와 레이아웃 추출.
  2. **API 캐싱 (localStorage)**: 추출된 대량의 텍스트를 LLM에 요청할 때, 구글 무료 API의 분당 요청 제한(Rate Limit)에 걸리지 않도록 문단 단위로 쪼개서 백그라운드에서 비동기로 요청. 한 번 분석된 결과는 `localStorage`에 캐싱하여 API 호출 비용 제로화.
  3. **워크시트 렌더링**: 분석된 지문 텍스트 중 핵심 단어에 하이라이트를 치고, 마우스 오버 시 툴팁(Dictionary)이 뜨도록 DOM 요소를 동적으로 생성.

### 2.3. 브라우저 내장 발음 평가 (Speech-to-Text Shadowing) — ✅ 완료 (2026-09-27)
> 구현 결과: `js/shadowing.js`의 단어 단위 Levenshtein 정렬로 정확(초록)·비슷함(노랑)·틀림/빠짐(빨강) 표시와 점수를 API 없이 즉시 계산. 숫자↔숫자 단어, 쪼개진 단어("to day"→today) 보정. [💡 AI 발음 팁]은 버튼을 눌렀을 때만 호출. 발음 탭·오늘의 영어·주간 학습지·PDF 쉐도잉에 공통 적용.

- **기능 개요**: 원어민 문장을 듣고 사용자가 마이크에 대고 따라 읽으면(Shadowing), 사용자의 발음을 인식하여 틀린 단어를 정확히 짚어주는 기능.
- **동작 방식 (기획 상세)**:
  1. **Web Speech API**: 별도의 외부 API 키 연동이나 백엔드 오디오 전송 없이, 웹 브라우저(Chrome)에 내장된 무료 `SpeechRecognition` 객체를 사용하여 STT(사용자 음성 -> 텍스트) 구현.
  2. **유사도 검사 알고리즘 (Levenshtein Distance)**: 원본 영어 문장(Target)과 사용자가 마이크로 읽어서 변환된 텍스트(Result) 간의 문자열 유사도를 프론트엔드 JavaScript 알고리즘으로 비교.
  3. **시각적 피드백**: 틀린 단어는 빨간색(Error 색상)으로, 맞춘 단어는 초록색(Success 색상)으로 렌더링하여 사용자에게 직관적인 피드백 제공.

> ⚠️ **Phase 4(다국어) 대비 사항**: Phase 2 기능을 만들 때부터 프롬프트·TTS·STT·캐시 키에 `lang` 값(기본값 `'en'`)을 받도록 설계하십시오. 지금은 영어만 쓰더라도, 나중에 일본어·스페인어를 붙일 때 다시 뜯어고치지 않아도 됩니다. (자세한 내용은 Phase 4 참고)

## 🔄 Phase 2.5: 기기 간 동기화 (휴대폰 ↔ PC) — ✅ 완료 (2026-09-27)
> 구현 결과: 단어장 탭 하단 "🔄 기기 간 동기화" 카드. 26자리 동기화 코드(또는 QR 링크 `#sync=`)로 연결. D1 DB `ai-language-tutor-db`는 첫 배포 때 자동 생성되어 `wrangler.jsonc`에 ID 고정. 테이블은 설계안의 3개 대신 `sync_items(kind, id, ...)` 하나로 통합. 단어장·오늘의 영어 아카이브·관심사 동기화, 삭제 전파, 앱 복귀·재연결 시 자동 동기화. 사용자가 D1을 직접 만들 필요 없었음.

### 문제
- 단어장(`ai_tutor_vocabulary`), 오늘의 영어 아카이브(`daily_archive`), 관심사(`vocab_interests`)가 모두 **브라우저 `localStorage`에만 저장**됩니다.
- 휴대폰에서 저장한 단어·추천 기록이 PC에 보이지 않고, 브라우저 데이터를 지우면 영구히 사라집니다.

### 목표
- 어느 기기에서 열어도 같은 단어장과 추천 기록을 봄.
- 인터넷이 끊겨도 지금처럼 동작(`localStorage`가 1차 저장소). 연결되면 서버와 맞춰 줌.
- 회원가입·비밀번호 없이 사용.

### 저장소: Cloudflare D1 (SQLite)
- 이미 쓰고 있는 Cloudflare Worker(`ai-language-tutor`)에 D1 데이터베이스를 바인딩으로 연결. 무료 요금제 한도(저장 5GB, 하루 읽기 500만 행)로 개인 사용에는 충분.
- KV 대신 D1을 고른 이유: 두 기기가 동시에 저장해도 **행(단어 1개, 추천 1세트) 단위로 합칠 수 있음**. KV는 사용자 데이터 전체를 한 덩어리로 덮어써서, 마지막에 저장한 기기가 다른 기기의 변경을 지울 위험이 있음.
- 테이블 설계 (모든 행에 `sync_id`로 소유자 구분):
  - `daily_sets(id, sync_id, date, at, themes_json)` — 추천 세트. 추가만 하고 수정하지 않음.
  - `vocab(id, sync_id, word, data_json, updated_at, deleted)` — 단어. 삭제도 `deleted=1`로 기록해야 다른 기기에 삭제가 전파됨.
  - `settings(sync_id, key, value, updated_at)` — 관심사 등.

### 기기 연결 방식: "동기화 코드"
- 첫 기기에서 [동기화 켜기] → 추측할 수 없는 무작위 코드(128비트, 예: `7KQ2-M9XD-...`) 생성. 휴대폰으로 옮기기 쉽게 QR 코드도 표시.
- 두 번째 기기에서 코드를 입력하면 같은 데이터를 공유.
- 서버에는 코드 원문이 아니라 **SHA-256 해시만 저장**. DB가 유출돼도 코드를 알아낼 수 없음.
- ⚠️ 코드를 아는 사람은 데이터를 읽고 쓸 수 있으므로 비밀번호처럼 취급. 코드를 잃어버려도 각 기기의 `localStorage` 데이터는 남아 있음.
- (선택, 나중에) 더 강한 보호가 필요하면 Cloudflare Access(Zero Trust 무료, 이메일 인증 코드 로그인)로 사이트 전체를 잠그는 방법도 있음.

### API (Worker에 추가)
- `POST /api/sync` — `{ since, changes: { daily_sets: [...], vocab: [...], settings: [...] } }`를 보내면 서버가 저장하고, `since` 이후 다른 기기에서 바뀐 항목을 돌려줌. 헤더 `Authorization: Bearer <동기화 코드>`.
- 합치기 규칙:
  - 추천 세트: `id`(생성 시각 + 첫 문장)로 중복 제거, 추가만.
  - 단어: 같은 `id`면 `updated_at`이 더 최근인 쪽이 이김 (복습 기록 SM-2 포함).
  - 설정: 키별로 최근 값이 이김.
- 동기화 시점: 앱을 열 때, 단어 저장·삭제·복습 직후(2초 모아서 한 번), 추천을 새로 받은 직후.

### 프론트엔드 변경
- `js/sync.js` (신규): 변경 기록 큐, 서버 전송, 받은 변경을 `localStorage`에 반영.
- `js/vocabulary.js`: 각 단어에 `updatedAt` 기록, 삭제 시 바로 지우지 않고 `deleted` 표시 후 동기화 완료 시 정리.
- 설정 영역에 [동기화 켜기 / 코드 입력 / 마지막 동기화 시각] UI.

### 사용자가 직접 해야 하는 작업
1. Cloudflare 대시보드 → **스토리지 및 데이터베이스 → D1 → 데이터베이스 만들기** (이름 예: `ai-tutor-db`).
2. 생성된 **데이터베이스 ID**를 AI에게 전달 (비밀 정보 아님). AI가 `wrangler.jsonc`에 바인딩을 추가하고 push하면 자동 배포.

### 작업 전에 먼저 고칠 것
- 미니 사전의 [단어장에 추가] 버튼이 `saveWord(단어문자열)`로 호출되어 **단어가 빈 값으로 저장되는 버그** (`js/app.js` 미니 사전 부분). 깨진 데이터가 다른 기기로 퍼지지 않도록 동기화 전에 반드시 수정.

### 3.1. 자료실 탭 (Resources)
- **기능 개요**: 위 표의 링크형 자료를 언어별 카드로 모아 보여주는 탭.
- **동작 방식**:
  1. `data/resources.json`에 `{ lang, title, desc, url, license, type: "link" | "builtin" }` 형태로 자료 목록을 저장.
  2. `index.html`에 '📚 자료실' 탭을 추가하고, 상단에 언어 필터(EN / JP / ES)를 둠.
  3. JLPT·DELE처럼 PDF로 받는 자료 카드에는 **[PDF 워크시트로 열기]** 안내 버튼을 달아 Phase 2.2 업로드 화면으로 연결.

### 3.2. 레벨 시스템 (CEFR / JLPT / DELE)
- **기능 개요**: 사용자가 자기 수준을 고르면, 모든 AI 생성 문장(오늘의 영어, 관심사 예문, 역할극 등)이 그 수준에 맞게 나오는 기능.
- **레벨 대응표** (조사 문서 기준, 대략적인 대응):

| 앱 레벨 | 영어 (CEFR) | 일본어 (JLPT) | 스페인어 (DELE) | 문장 규칙 (프롬프트에 주입) |
|---|---|---|---|---|
| 기초 | A1~A2 | N5~N4 | A1~A2 | 단문 중심, 8단어 이내, 현재·단순 과거 |
| 중급 | B1~B2 | N3~N2 | B1~B2 | 접속사·관계사·완료·가정법 포함 복합문, 10~18단어 |
| 고급 | C1~C2 | N1 | C1~C2 | 관용구·수사법·미묘한 뉘앙스, 20단어 이상 |

- **동작 방식**:
  1. `localStorage`의 `user_level`(`'basic' | 'intermediate' | 'advanced'`)에 저장. 헤더 또는 설정 영역에 레벨 선택 UI 추가.
  2. `js/prompts.js`에 `getLevelRule(level, lang)` 함수를 만들어 위 표의 "문장 규칙"을 문자열로 돌려주고, `daily` / `custom_example` / `roleplay` / `examples` 프롬프트 끝에 붙임.

### 3.3. 주제별 예문 생성기 (Topic Examples)
- **기능 개요**: 레벨 × 주제를 고르면 실전 예문 5개를 받아 보고, 단어를 바로 단어장에 추가하는 기능.
- **주제**: 비즈니스·이메일 / 여행·식당 / IT·개발 / 일상·감정 + 사용자 관심사(기존 `vocab_interests` 값 재사용).
- **프롬프트 (`mode: 'examples'`)**: 조사 문서의 템플릿을 기반으로 하되, **두 가지를 반드시 수정**합니다.
  1. **최상위를 배열이 아닌 객체로 감쌀 것.** 서버(`server/main.py`)는 `re.search(r'\{.*\}', ...)`로 `{ }` 객체만 잘라내므로, 템플릿처럼 `[...]` 배열로 응답하면 파싱이 깨지거나 첫 항목만 잘립니다.
  2. 필드명을 기존 코드 관례(`ko`)에 맞춤.
  ```json
  { "examples": [ { "sentence": "...", "ko": "한국어 해석", "reading": "(일본어일 때만) 후리가나", "keyVocabulary": [ { "word": "...", "meaning": "..." } ] } ] }
  ```
- **캐싱**: `examples_{lang}_{level}_{topic}` 키로 `localStorage`에 저장. 먼저 캐시를 확인하고, 없거나 사용자가 **[새 예문 받기]**를 눌렀을 때만 API 호출.

### 3.4. 퍼블릭 도메인 예문 코퍼스 구축 (선택, 후순위)
- **기능 개요**: FSI·VOA·Tatoeba 문장을 미리 가공해 앱에 내장. API 호출 없이도 레벨·주제별 예문을 즉시 보여줄 수 있음.
- **동작 방식**:
  1. 로컬 PC에서 돌리는 가공 스크립트 `server/tools/build_corpus.py` 작성 (배포 대상 아님).
  2. Tatoeba는 공식 CSV 내보내기 파일을, FSI·VOA는 스크립트 텍스트를 입력으로 받아 문장 단위로 분리.
  3. 문장 길이 규칙으로 1차 레벨 분류 → 애매한 문장만 LLM으로 레벨·주제 태깅 (분당 요청 제한을 고려해 천천히 배치 처리).
  4. 결과를 `data/corpus/{lang}.json`에 `{ text, ko, level, topic, source, license, author }` 형태로 저장. **`source`/`author`는 출처 표기 의무 때문에 반드시 유지.**
  5. 용량 관리: 언어당 수천 문장 이내로 유지. FSI MP3 오디오는 용량이 크므로 저장소에 넣지 말고 원본 링크로 연결하거나 TTS로 대체.

## 🌏 Phase 4: 다국어 확장 (일본어 · 스페인어)

궁극적으로 영어뿐 아니라 일본어·스페인어도 같은 앱에서 배울 수 있게 하는 계획입니다. 현재 코드는 곳곳에 영어가 하드코딩되어 있으므로, **먼저 "학습 언어" 설정 구조를 만든 뒤** 기능별로 언어를 붙여 나갑니다.

### 4.1. 학습 언어 설정 구조 (기반 작업)
- `localStorage`의 `target_lang` (`'en' | 'ja' | 'es'`, 기본값 `'en'`)에 학습 언어를 저장하고, 헤더에 언어 전환 스위치(🇺🇸 / 🇯🇵 / 🇪🇸)를 둠.
- 신규 파일 `js/languages.js`에 언어별 설정을 한곳에 모음:
  ```js
  export const LANGS = {
    en: { name: 'English',  nameKo: '영어',     speechCode: 'en-US', levelSystem: 'CEFR', spaced: true  },
    ja: { name: 'Japanese', nameKo: '일본어',   speechCode: 'ja-JP', levelSystem: 'JLPT', spaced: false },
    es: { name: 'Spanish',  nameKo: '스페인어', speechCode: 'es-ES', levelSystem: 'DELE', spaced: true  },
  };
  ```
- 탭 이름('오늘의 영어 추천' 등)도 선택된 언어 이름으로 바뀌게 함.

### 4.2. 프롬프트 다국어화 (`js/prompts.js`)
- `getSystemPrompt(mode)` → `getSystemPrompt(mode, lang)`로 변경하고, 프롬프트 안의 "English"를 `LANGS[lang].name`으로 치환.
- **주의**: 현재 `dictionary` 프롬프트에 "NEVER use Chinese (中文) or Japanese (日本語)" 규칙이 있음. 원래는 해설에 중국어·일본어가 섞이는 걸 막으려는 규칙이지만, 일본어 사전 모드에서는 표제어·예문이 일본어여야 하므로 **"해설은 한국어로, 표제어·예문은 학습 언어로"**라는 규칙으로 바꿔야 함.
- `translation` 모드는 "ko↔en"을 "ko↔{학습 언어}"로 변경.
- 일본어 응답에는 `reading`(후리가나) 필드를 추가로 요구.

### 4.3. 데이터 언어별 분리
- **단어장** (`ai_tutor_vocabulary`): 각 단어에 `lang` 필드 추가. 기존에 저장된 단어는 앱을 처음 열 때 한 번 `lang: 'en'`으로 자동 변환(마이그레이션). 단어장 화면은 현재 학습 언어의 단어만 보여줌.
- **캐시 키**: `daily_sentence` → `daily_sentence_{lang}`처럼 모든 캐시 키에 언어 코드를 붙임.
- **워크시트** (`data/worksheet.json`): 영어 전용이므로 그대로 두고, 일본어·스페인어는 Phase 3.4에서 만든 FSI 기반 유닛으로 별도 파일 구성.

### 4.4. 음성 (TTS / STT)
- 현재 하드코딩된 `'en-US'` (`js/speech.js:14`, `js/app.js:644`, `js/app.js:657`)를 `LANGS[lang].speechCode`로 교체.
- 기기·브라우저마다 일본어·스페인어 음성 설치 여부가 다르므로, `speechSynthesis.getVoices()`로 해당 언어 음성이 있는지 확인하고, 없으면 "이 기기에는 ○○어 음성이 없습니다" 안내 표시.

### 4.5. 발음 채점(Phase 2.3)의 언어별 처리
- **영어·스페인어**: 소문자 변환 + 문장부호 제거 후 단어 단위 비교. 스페인어는 악센트(á, é, ñ)를 무시하는 "관대한 채점" 옵션 제공 (음성 인식이 악센트를 빠뜨리는 경우가 많음).
- **일본어**: 띄어쓰기가 없어 단어 단위 비교가 불가능. 또 음성 인식 결과가 한자/가나를 원문과 다르게 표기하는 경우가 잦음 (예: 원문 `ありがとう` ↔ 인식 `有難う`).
  → **문자 단위 Levenshtein 비교**로 1차 채점하고, 점수가 애매하면 기존 `pronunciation` 모드 LLM에 "읽는 소리가 같은지" 최종 판정을 맡김.

### 4.6. 원클릭 미니 사전의 언어별 처리
- **단어 쪼개기**: 일본어는 띄어쓰기가 없어 클릭한 단어를 찾을 수 없음. 브라우저 내장 `Intl.Segmenter('ja', { granularity: 'word' })`로 단어를 분리 (외부 라이브러리 불필요).
- **사전 데이터**: Free Dictionary API는 영어 전용이므로, 일본어·스페인어는 LLM `dictionary` 모드로 조회.

### 4.7. 일본어 읽기 보조 (조사 문서의 'No-Text 회화 모드' 반영)
- 일본어 문장 위에 `<ruby>` 태그로 후리가나 표시.
- 읽기 힌트 설정: **[후리가나 / 한글 독음(예: 곤니치와) / 숨김]** 중 선택. 가나를 아직 못 읽는 입문자는 TTS를 듣고 한글 독음만 보며 따라 말하는 모드로 학습.
- 스페인어는 철자대로 읽는 언어라 기본은 숨김, 기초 레벨에서만 한글 독음 옵션 제공.

### 4.8. 유튜브 자막 (서버 수정 필요)
- `server/main.py:61`의 자막 언어 목록이 `['ko', 'en', 'en-US', 'en-GB']`로 고정되어 있음 → 요청 바디에 `lang`을 받아 `ja` / `es` 자막도 우선 조회하도록 변경.
- 자막이 없어 Groq Whisper로 받아쓰기할 때도 `language` 파라미터를 전달해 인식 정확도를 높임.
- ⚠️ 서버 파일 수정이므로, 수정 후 사용자 PC에서 `run_server.bat`로 **서버를 재시작해야 반영됨**. (API 키·CORS·Ngrok 설정 부분은 건드리지 않음)
